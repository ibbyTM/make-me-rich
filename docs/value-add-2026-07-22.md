# Value-Add scoring (2026-07-22)

Read-only enrichment layer measuring price attractiveness vs. a local
commercial rental-value benchmark. Same pattern as Data Centre Fit: pure
function inputs/outputs, reasons always human-readable, weights/thresholds
named constants for later tuning.

**Flood risk removed (2026-07-22, same day):** the score originally split
75/25 between price and flood risk. Dropped flood risk entirely at the
user's direction — not a priority, and it was only ever a coarse
postcode-prefix guess-list (never a real Environment Agency lookup)
anyway. Score is now 100% the price-percentile signal described below.
`src/geo/floodRisk.ts` and its data are no longer used anywhere in the
codebase.

## Data source pivot: Land Registry → VOA business rates

The first build used HM Land Registry Price Paid Data as the price
comparable. Before wiring it to real numbers, we verified its scope against
gov.uk's own guidance and found **Price Paid Data is residential-sales-only**
("all residential property sales in England and Wales") — every listing in
this dashboard is commercial (Barnsdales, Rightmove Commercial, SMC Brownill
Vickers), so comparing a warehouse's asking price to nearby house sale
prices would have produced a scorecard that looked precise while comparing
two markets that don't move together. No amount of engineering fixes a wrong
data source, so we stopped and switched.

**VOA (Valuation Office Agency) business rates** is the free, no-auth,
genuinely commercial-specific alternative: a "rateable value" (VOA's
professional estimate of a property's annual market rent) for every
non-domestic property in England & Wales, published as a national bulk CSV.
It's a *rental* figure, not a *sale price* — there's no free, verifiable
source for the yield (rent-to-price) multiple that would convert one into
the other, and inventing one would look precise while being fabricated.
Instead, the score ranks each listing's own (price/sqft ÷ local VOA
rate/sqft) ratio by **percentile** against every other scored listing — a
real, relative "cheaper than its peers, controlling for location" signal,
without pretending to know the area's true cap rate.

## Scoring Model

**100-point scale, one component:**

**Price attractiveness (100 pts)** — percentile rank of
`(price/sqft) ÷ (local VOA district median rate/sqft)` across every
scoreable listing in the dataset. Lower percentile = cheaper relative to
its local commercial rental-value benchmark = more points.
- ≤20th percentile: 100 pts
- ≤35th: 80 pts
- ≤50th: 60 pts
- ≤65th: 35 pts
- ≤80th: 15 pts
- >80th: 0 pts
- Gated on: listing has a price and size, its postcode district has a VOA
  benchmark, and that benchmark has ≥10 samples (all 20 districts in the
  live dataset clear this by a wide margin — hundreds to low thousands of
  samples each).

**Bands** (thresholds; will retune once the real distribution is visible
across more districts):
- `strong`: score ≥65
- `possible`: score 35–65
- `unlikely`: score <35
- `insufficient_data`: no price/size, no VOA benchmark, or couldn't be
  percentile-ranked

## Data Pipeline

**VOA business rates** (`scripts/voa-rates-fetch.ts` + `src/geo/voaRates.ts`):
- Downloads the national "summary valuations" compiled list
  (~90MB compressed / ~730MB uncompressed — every non-domestic rateable
  property in England & Wales) from
  `voaratinglists.blob.core.windows.net`, free, no auth.
- **Field layout is not fixed-width** — the address portion has a variable
  number of populated sub-fields per row, which shifts every column after
  it. Confirmed by manually diffing real rows: fixed-index parsing silently
  misaligns fields on some rows. Fixed by locating the postcode via regex
  (its shape is unambiguous) and reading every other field at a *relative*
  offset from the postcode's position — consistent across rows.
- Excludes `OTH`-unit records (non-area units like car-parking "per space")
  — only `GIA`/`NIA`/`GEA`/`EFA` (real floor-area measures) are used.
- Streams the file line-by-line (never loaded fully into memory), filters
  to only the postcode districts present in the current dashboard data, and
  writes a small per-district median-£/sqft table.
- The 730MB national file is cached under `.cache/voa/` (gitignored,
  re-downloaded only if missing); only the small filtered JSON output
  (`dashboard/data/voa-rates-comparables.json`) is committed.
- Verified against the live 220-row dataset: 20 postcode districts, 22,680
  matching VOA records, all 20 districts clearing the 10-sample confidence
  threshold with 419–2,163 samples each. Medians follow a sensible
  geography gradient (£5–9/sqft in secondary Midlands/North locations,
  £13–18/sqft in Manchester).

## Implementation

- **src/scoring/valueAdd.ts**: Pure scoring function —
  `scoreValueAdd(input)` → `{ score, band, reasons }`. No side effects;
  reasons array explains every point, including the actual £/sqft figures
  and percentile.
- **src/geo/voaRates.ts**: `parseVoaSummaryLine()` (regex-anchored,
  relative-offset field extraction), `ratePerSqft()` (unit-aware, excludes
  `OTH`), `median()`.
- **scripts/voa-rates-fetch.ts**: Download + stream-filter + precompute
  orchestration.
- **scripts/value-add-listings.ts**: Two-pass scoring — pass 1 computes
  every row's raw ratio; pass 2 ranks each ratio's percentile against the
  full set, then scores. Writes the `valueAdd` field back onto each row
  in place (no deletions, same pattern as dedup/data-centre-fit).
- **Dashboard UI**: "Value-Add Score" filter (All/Strong/Possible/
  Unlikely), sort option, card tag "Value-Add: {band} ({score})" with the
  £/sqft-vs-benchmark reasoning on hover.

## Test Coverage

**test/valueAdd.test.ts**: 9 unit tests — percentile bands, insufficient-data
gates (too few VOA samples, no benchmark, missing price/size, unrankable
row), score clamping, reason-string content.

## Ordering Note

Same caveat as dedup/data-centre-fit: `scripts/value-add-listings.ts` must
run after any fresh base pull (base report scripts wipe all enrichment
fields). Additionally, re-run `scripts/voa-rates-fetch.ts` whenever the set
of postcode districts in the dataset changes (new listings in a district
not yet covered by the comparables table will score `insufficient_data`
until it's re-run).

## Known Limitations

1. **Rateable value is a rental proxy, not a sale-price comparable.** The
   percentile-ranking design was chosen specifically to avoid needing a
   yield-multiple assumption, but it's still a relative signal ("cheaper
   than its peers by this measure"), not an absolute "X% below true market
   value" claim — the reasons text is written to reflect that.
2. **VOA data covers occupied/assessed non-domestic property**, not vacant
   land or the smallest exempt properties — a handful of dashboard listings
   (pure land sales, very small units) may never get a benchmark regardless
   of district coverage.
